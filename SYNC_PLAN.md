# Offline Sync — Technical Design

## Where Does the Offline Code Live?

**Everything is Flutter-side. Odoo requires zero changes.**

Odoo only ever receives normal JSON-RPC POST requests — it has no concept of whether the
app was online or offline when the user took an action. The Flutter app is responsible for:

- Detecting connectivity state
- Storing data locally when offline
- Queuing write operations
- Replaying those operations against Odoo when connectivity returns
- Handling conflicts and surfacing errors to the user

The boundary is clean: Odoo is the source of truth. Flutter buffers until it can reach
that source of truth.

---

## Sync Trigger Points

Three triggers must all be active simultaneously:

```
1. App foregrounded       → AppLifecycleState.resumed → SyncService.sync()
2. Connectivity restored  → connectivity_plus stream   → SyncService.sync()
3. User manual trigger    → "Sync now" button          → SyncService.sync()
```

`SyncService.sync()` is idempotent — calling it multiple times is safe. It checks the
queue and exits early if nothing is pending. A mutex/lock prevents concurrent sync runs
if multiple triggers fire at once.

Background sync (while the app is closed) is possible via the `workmanager` package.
iOS limits background tasks to roughly every 15 minutes. For a field sales app this is
acceptable — the officer opens the app when they return to the office.

## The Idempotency Problem (and Solution)

**The problem:** Network can cut out after Odoo processes a request but before the
response reaches the app. The app sees a timeout, retries, and creates a duplicate
record on Odoo.

**The solution: Client Reference UUIDs**

Every queued write includes a UUID generated by the Flutter app. Odoo stores it in a
client reference field. Before retrying a create, the app checks whether a record with
that reference already exists.

```dart
// When queuing offline:
final clientRef = 'MOBILE-${uuid.v4()}';
await _db.enqueueSyncOp(
  operation: 'create_order',
  payload: jsonEncode({
    ...orderPayload,
    'client_order_ref': clientRef,   // sent with every create request
  }),
  clientRef: clientRef,
);

// In SyncService before replaying a create:
// 1. Check if record with this client_order_ref already exists on Odoo
// 2. If yes → mark done, record the server ID, skip creation
// 3. If no  → create it normally
```

`client_order_ref` is an existing field on `sale.order` in Odoo 18. For other models
(distributors, employees), a similar reference field needs to be added on the backend
side. This is the only backend change the offline layer requires.

## The Dependency Chain Problem (and Solution)

**The problem:** Creating records offline gives them temporary local IDs (e.g. `-1`,
`-2`). Subsequent records that reference those IDs cannot be synced until the parent
is synced and a real server ID is known.

Example scenario:
1. Officer creates new distributor offline → local ID: `-1`
2. Officer assigns an employee to that distributor → payload has `distributor_id: -1`
3. App goes online
4. Distributor syncs → Odoo assigns real ID: `47`
5. Employee sync fires with `distributor_id: -1` → **Odoo rejects it** (no record -1)

**The solution: ID Mapping Table**

```
id_map
  local_id    INTEGER   -- temporary negative ID (e.g. -1, -2, -3...)
  server_id   INTEGER   -- real Odoo ID assigned after sync
  model       TEXT      -- 'res.partner', 'hr.employee', 'sale.order', etc.
```

Workflow:
```
1. Distributor create succeeds → store (local_id: -1, server_id: 47, model: 'res.partner')
2. Before replaying employee op → scan payload for local IDs
3. Substitute: distributor_id: -1  →  distributor_id: 47
4. Employee create fires with correct server ID
```

If an operation's payload contains a local ID with no mapping yet (parent hasn't synced),
the operation is skipped and retried on the next sync pass.

## Sync Order

Operations must be replayed in dependency order. Store an `operation_type` on each
queue row and sort by priority before replay:

```
Priority 1  →  distributors / res.partner creates
Priority 2  →  employees (may reference distributor IDs)
Priority 3  →  routes (may reference distributor IDs)
Priority 4  →  outlets / route lines (may reference route IDs)
Priority 5  →  sale orders (may reference distributor IDs)
Priority 6  →  van loading transfers (reference pre-existing location IDs — safe)
Priority 7  →  delivery validations (reference pre-existing picking IDs — safe)
```

Van loading and delivery operations are safe to replay without ID substitution because
the location and picking records already exist on Odoo before the officer ever goes
offline.

## Sync Queue Lifecycle

```
Created offline → status: 'pending'
                       │
SyncService picks it up → status: 'syncing'
                       │
          ┌────────────┴────────────┐
        Success                  Failure
          │                         │
  status: 'done'         retry_count < 3?
  record server_id             │ yes        │ no
  in id_map table       status: 'pending'  status: 'failed'
                        (retry next pass)   notify user
```

### Database Schema

```
sync_queue
  id               INTEGER PRIMARY KEY
  operation        TEXT      -- 'create_order', 'validate_transfer', etc.
  operation_type   TEXT      -- for priority sorting (see above)
  endpoint         TEXT      -- '/api/v1/sale-orders/create'
  payload          TEXT      -- full JSON blob including client_ref UUID
  client_ref       TEXT      -- UUID for idempotency check
  created_at       INTEGER   -- Unix timestamp (FIFO ordering within priority)
  status           TEXT      -- 'pending' | 'syncing' | 'done' | 'failed'
  retry_count      INTEGER   -- default 0, max 3
  error_message    TEXT      -- last server error, shown to user on failure

id_map
  id               INTEGER PRIMARY KEY
  local_id         INTEGER
  server_id        INTEGER
  model            TEXT
  created_at       INTEGER
```

## SyncService — Full Implementation Sketch

```dart
class SyncService {
  final ApiService _api;
  final LocalDatabase _db;
  bool _running = false;

  Future<void> sync() async {
    if (_running) return;           // prevent concurrent runs
    _running = true;
    try {
      await _processPending();
    } finally {
      _running = false;
    }
  }

  Future<void> _processPending() async {
    // Fetch in priority order, then by created_at (FIFO)
    final pending = await _db.getPendingSyncOps();

    for (final op in pending) {
      // Resolve any local IDs to server IDs
      final resolvedPayload = await _resolveLocalIds(op.payload);

      // If unresolved local IDs remain, parent hasn't synced yet — skip
      if (_hasUnresolvedLocalIds(resolvedPayload)) continue;

      try {
        await _db.markSyncing(op.id);

        // Idempotency check for create operations
        if (op.operation.startsWith('create_') && op.clientRef != null) {
          final existing = await _api.findByClientRef(op.operation, op.clientRef!);
          if (existing != null) {
            await _db.recordIdMapping(
              localId: op.localId,
              serverId: existing['id'],
              model: _modelForOperation(op.operation),
            );
            await _db.markDone(op.id);
            continue;
          }
        }

        final result = await _api.post(op.endpoint, jsonDecode(resolvedPayload));

        // Record the new server ID for dependent operations
        if (result['id'] != null && op.localId != null) {
          await _db.recordIdMapping(
            localId: op.localId!,
            serverId: result['id'] as int,
            model: _modelForOperation(op.operation),
          );
        }

        await _db.markDone(op.id);

      } catch (e) {
        final newCount = op.retryCount + 1;
        if (newCount >= 3) {
          await _db.markFailed(op.id, e.toString());
          // surface to user — see UI section below
        } else {
          await _db.incrementRetry(op.id, e.toString());
        }
      }
    }
  }

  Future<String> _resolveLocalIds(String payload) async {
    // Scan payload for negative integers, look them up in id_map,
    // substitute with server IDs, return updated JSON string
    ...
  }
}
```

## Stock Conflict Handling

Van loading and delivery validation are the two operations where Odoo will reject the
sync if stock quantities have moved since the user queued the operation.

This cannot be prevented — it can only be handled gracefully.

**Failure flow:**

```
Sync attempt → Odoo returns ValidationError:
  "Requested 10 units of [Product X] but only 4 available."
             → Mark queue item as 'failed'
             → Store Odoo's error_message in the row
             → Show user in Sync Failures screen
```

**User options on failure:**

| Action | Behaviour |
|--------|-----------|
| Retry  | Reset `retry_count` to 0, `status` to `pending`, retry on next sync |
| Edit   | Open transfer form pre-filled with their original payload, let them adjust quantities |
| Discard | Delete the queue row — the transfer is abandoned |

## UI Requirements

The user must have visibility into the queue state at all times.

### Sync Status Badge (persistent, in app header)

```
[↑ 3 pending]    — items waiting to sync
[⟳ syncing...]  — sync in progress
[✓ synced]       — all clear
[⚠ 2 failed]    — items need user attention
```

### Pending Sync Screen

Accessible from the badge or settings. Shows:

```
Pending (2)
───────────────────────────────
↑  Create Sale Order            queued 10 min ago
   SO for Distributor: ABC Ltd

↑  Validate Transfer            queued 25 min ago
   Van loading — Location: Van 3

Failed (1)
───────────────────────────────
✕  Validate Transfer            failed 5 min ago
   Van loading — Location: Van 3
   "Requested 10 units of Mineral Water but only 4 available."
   [Retry]  [Edit]  [Discard]
```

### Last Synced Timestamp

Shown on any screen with cached data:

```
Distributors  ·  Last updated 2h ago
```

## What Odoo Needs vs. What It Already Has

| Requirement | Status |
|-------------|--------|
| Normal JSON-RPC API calls | Already exists — no changes |
| `client_order_ref` on `sale.order` | Already a standard Odoo field |
| Client ref field on `res.partner` (distributors) | Needs backend addition |
| Client ref field on `hr.employee` | Needs backend addition |
| Find-by-client-ref query endpoint | Needs backend addition |

The four items marked "needs backend addition" are the only Odoo-side work required for
offline support. The Flutter app does everything else.

## Risk Summary

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Duplicate records from retry without idempotency | High (without fix) | Client ref UUID + check before create |
| Orphaned child records (missing parent ID) | High | ID mapping table, skip until parent syncs |
| Stale stock causing transfer rejection | Medium–High for field use | User-visible failure + edit/retry/discard |
| Data loss if queue is cleared on logout | Low | Never clear `pending` or `failed` rows on logout |
| iOS background sync unreliable | Medium | In-app foreground sync covers 95% of cases |
